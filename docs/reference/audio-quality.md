# Music fidelity, device routing and tuning review

## Problems reproduced, not assumed

The regression suite reproduced three earlier gain-staging errors: disabling the music stage still changed amplitude; bypass retained attenuation reserved for disabled EQ filters; and reserving headroom independently in two stages could over-attenuate the signal. The current engine identifies itself as `music-fidelity-7`. Original Maris built-ins request neutral preamp where appropriate, positive cascades reserve calculated headroom once across the combined chain, and the final linked sample-peak limiter remains active. Compatibility handling preserves deliberate custom preamp choices. Fidelity 7 retains the physical-output correction-first startup/rebind ramp and adds bounded spatial controls. Virtual 360 processes only the Side channel above the bass region through all-pass decorrelation; mono/center content remains unchanged. Stereo Focus attenuates Side energy without moving Mid.

The clock bridge uses a preallocated 128-tap, 257-phase Blackman-windowed sinc interpolator for supported 44.1–192 kHz sample-rate conversion and near-unity independent-clock correction. Downsampling narrows the reconstruction passband. Existing frequency-response fixtures do not establish full-system latency or subjective fidelity. Parameter updates retain unchanged state and use the existing bounded crossfade path.

## Device correction, preference and output switching

Device correction and listening preference remain separate. Imported or AutoEq-derived filters are correction evidence; Bass, Presence, Air, Softness, Width, Dynamic EQ, Bass Assist and compression are preferences/enhancements. Context-aware tuning is forbidden from editing correction filters or correction preamp/provenance.

The native macOS process-tap path does not change system volume or the macOS default output. Output preference identity uses CoreAudio device UID/model-UID evidence when available; a rename keeps the stable binding, and distinct same-named stable devices receive distinct profile keys instead of silently sharing correction. Maris may pin its own render stream to a selected physical endpoint. The TUI no longer changes hardware merely when `O` is pressed: `O` opens a picker and Enter is required. If a pinned endpoint disappears, the native session releases the old path, unpins, rebuilds against the current system default, and recompiles the effective listening profile and capability state for the new endpoint. Every newly built native output pipeline starts from the target device's correction with Bass/Presence/Air/Softness/Width/Balance/compression/adaptive/Bass Assist neutral, then queues the saved subjective target as a 120 ms full-chain crossfade; correction filters, correction preamp and high-pass evidence are preserved in the baseline. A failed requested switch attempts the current system default rather than intentionally leaving playback stranded. These code paths and control messages are tested, but broad Bluetooth/hotplug behavior still requires real-device listening validation.

The simple selected-application session can capture several PIDs into one shared DSP/output path; exiting processes are removed and the route is released when none remain. The mixer is the independent path: each application or hardware source can own its own strip with gain, pan, sends, EQ and compression, plus explicit speech-only RNNoise when enabled. macOS uses separate process taps, Linux separate private routes, and Windows separate process-loopback captures. These paths do not change endpoint master volume or the OS default output.

AutoEq discovery is pinned to commit `7ae0f56d53074872b028649617a22bbb4232feb7`. The recommended-model index is vendored and release builds assemble an embedded profile pack from that exact revision. Exact unique endpoint names may auto-apply; fuzzy and variant matches require confirmation; generic endpoint names never silently select a headphone model. Confirmed local profiles remain valid overrides and explicit endpoint-to-model binding uses the same validation. None of this proves that a physical unit, fit, pads or ANC mode match the measurement.

## Dynamic EQ, Virtual Bass and loudness evidence

The bounded adaptive controller uses three relative-energy detectors around low-frequency buildup, upper-mid harshness and high-frequency prominence. It remains cut-only; it never generates a dynamic boost. Virtual Bass/Bass Assist derives bounded harmonics from low-frequency content and is off by default.

The context-aware planner combines real signal evidence, device capability, the bound correction state, the current user preference and semantic context only when an integrated semantic backend actually supplies it. Genre remains only one semantic factor: sufficiently confident vocal probability/instrument tags can support a small presence decision, while bright-instrument or soft/mellow mood tags affect de-harshing only when measured treble evidence independently supports the change. Bass-heavy material never receives an additional static bass boost. Unknown physical limits block speculative sub-bass enhancement. A known limited compact speaker can prefer bounded Bass Assist over a large low shelf. A measured/corrected headphone with available headroom can receive a small bounded preference boost. Stereo widening is blocked/reduced when measured correlation is already low.

The analysis worker uses `ebur128` for momentary, short-term and integrated loudness plus true-peak evidence. This does not turn the final output limiter into a true-peak limiter and does not estimate acoustic SPL.

## Music Context and model boundary

A background Music Context worker consumes complete analysis windows outside the audio callback. The integrated fallback is `signal-only-v1`: it publishes bass/treble energy, crest, correlation, RMS and loudness evidence while leaving genre, instruments, mood and vocal/instrumental probabilities empty. Signal-only mode therefore cannot be mistaken for semantic recognition.

MusicNN is the local semantic context backend in release builds. Its fixed contract is 16 kHz mono, 512-point Hann STFT, 256-sample hop, 96 mel bands and `log10(10000*x + 1)`, with approximately three-second patches. The reviewed PyTorch-port revision and safetensors SHA are recorded in [third-party components](third-party.md). `build.rs` accepts only that pinned artifact and exact SHA before embedding it; normal runtime has no model fetch/import command and never executes Hugging Face custom code. The native Candle adapter runs only on the background context worker. If the model resource is absent or inference fails, the result falls back to signal-only evidence rather than inventing semantic labels.

RNNoise remains an explicit speech-only path. It is never the default music enhancer.

## Rewritten real-data console

The Studio Dashboard replaces the four mandatory workspaces and equal-card grid with a dominant analyzer, fixed device/control rail, docked stereo meters and subordinate music-context/AI/mixer/health areas. E/M/V/I/H or visible actions open fixed-position EQ, Apps, Device, Listening Assist and Health inspectors; Tab is optional and Esc returns home. All ten primary listening controls remain available on the default surface. The profile EQ and pre-EQ spectrum share a frequency axis but retain separate labeled vertical scales; no acoustic-response or post-EQ measurement is implied. Stale/future/missing telemetry is not rendered as live signal. Small terminals retain the compact monitor and confirmation overlays. The visual-review probe measures deterministic generated audio, exports actual Ratatui cells and labels every image as an offline fixture; it does not start system capture.

Risky changes use bounded overlays. Opening the output picker does not change the route; opening the preset picker does not change the profile; Listening Assist preview does not apply itself. Only useful implemented processing appears in the customer workflow. Unused research models are absent from the normal UI. MusicNN tags appear only when the bundled backend produces current, sufficiently confident context; otherwise the home panel uses measured signal features. Unknown telemetry remains explicit.

The palette is signal/semantic aware. Semantic palettes require actual semantic context; otherwise only measured signal features can select a signal theme. A 1.25-second debounce and 0.65-second smooth transition reduce theme flicker. The same tracker drives the TUI and macOS compact monitor.

The Studio meters now include a fixed dBFS scale and fixed warning zones. Dynamic-EQ reduction is read from telemetry rather than inferred from configured strength. LUFS/true-peak/RMS are shown only for a fresh analysis window with the current sample rate. The applied-state header needs both audio revision counters; missing or stale telemetry cannot claim successful application. These are UI evidence safeguards, not additional hardware or listening validation.

The spectrum uses real pre-EQ telemetry and stale/inactive data decay. No decorative random spectrum or level motion is generated. Text dialogs remain bounded to 66 columns; the scene picker uses at most 84 columns for its list and preview, always clipped to the actual terminal area.

## Real-time and performance boundary

Audio callbacks remain free of model inference, network access, file IO, application mutexes and logging. Music Context inference is background-only, receives bounded worker windows, rate-limits semantic backend submissions, and resets stale context after output rebinding. Runtime status exposes queue depths, xruns, model latency, callback count/frames, total callback processing time converted to average real-time-budget percentage, and maximum callback processing microseconds. This timing is measured callback wall time, not whole-process CPU utilization; worker CPU remains null rather than fabricated.

The requested CPU/latency targets still require measurement on real devices and builds. Passing offline tests is not evidence that every hardware combination meets a 2–3% CPU target or a particular end-to-end latency.

## Commercial-convergence control regressions

The live preview gate now rejects future or stale runtime/analysis timestamps, mismatched sample rates, incomplete windows and insufficient signal. A cached or stale semantic object cannot promote itself into a usable model result. The previously abrupt bass-heavy preference rule is corrected to reduce a positive bass setting by 0.5 dB toward zero before device constraints, rather than snapping it to zero. Low-crest material does not silently enable a compressor. Manual compression remains supported.

Displayed deltas are derived from the final device-constrained profile, including boolean changes. Apply checks the target and explanation; an unchanged target retains both revision and the prior undo snapshot. Synthetic tests establish these invariants, not subjective improvement.

`cargo run --release --locked --example engine_probe` exercises the native DSP and embedded RNNoise network using generated stereo tones/noise. The separate MusicNN tests execute the bundled checkpoint and fixed preprocessing on CPU. These results cover finite output, deterministic inference and offline timing only; they do not capture hardware audio, measure end-to-end latency or establish listening preference. [Model decisions](../development/models.md) and [product gates](../development/product-gates.md) define the remaining release evidence.

## Listening scenes and language regression boundary

Ten original listening scenes reuse the existing validated DSP: focus, long listening, dialogue, cinema, night dialogue, acoustic, orchestral, tight bass, game clarity and small speakers. Their initial static gains are deliberately modest, stereo width stays at unity, and only the explicitly labeled new night-dialogue scene enables compression. The existing night preset is retained. No scene starts RNNoise or another speech model, changes OS volume, claims surround/positional processing, or represents a measured acoustic correction. Small-speaker virtual bass remains disabled unless device capability allows it and a low-frequency floor is known.

Preview and apply share final device-constrained construction. Correction filters, source, preamp, high-pass, channel balance and comparison policy survive scene selection; original EQ revision remains unchanged. Regression tests exercise all ten scenes at 44.1, 48, 96 and 192 kHz through the real deterministic DSP with generated over-level/nonfinite fixtures and check finite sample-peak-limited output. These are numerical safety and state-isolation checks, not subjective listening results.

Localization remains presentation-only: translated planner deltas and explanations never replace the canonical serialized proposal. Tests render six locales across home, all inspectors, scene/output/help/start/AI overlays and multiple terminal sizes; other tests verify template placeholders, device-name preservation, menu-language propagation mechanisms and CLI/MCP identifiers. Native menu appearance on every OS still needs platform validation; raw unfamiliar OS errors retain their technical cause.

## Menu and configuration safety

The menu quick-control refactor changes the UI/control plane, not DSP coefficients, clocks, limiters or callback processing. Preset/output selection stages a preview and explicit apply checks session, endpoint UID/profile binding, rebind count, sample rate and both revisions. Failed or stale selections do not silently rebase to a new endpoint. A malformed output command is rejected rather than interpreted as system-default following. Concurrent UI/agent requests cannot silently overwrite the same pending command slot; Stop retains priority. Invalid action/rebind guards become control failures rather than fatal audio-session errors.

A/B uses the same listening revision/validation path but no longer replaces the tonal undo snapshot or changes the TUI's last tonal-edit domain. Exact no-op writes do not consume history. Current-device Undo checks for unrelated-device/default changes before restoring. The existing global bypass also forces the music reference branch; the menu and comparison indicator now say processing is bypassed instead of implying that only the original EQ is bypassed or that the enhanced branch is audible. This does not alter the existing shared gain or final limiter.

Additional regression coverage includes preview cancellation, expiry, future timestamps, route/capability/revision drift, same-name output identities, missing telemetry, competing writers, missing/malformed output fields, discrete key repeats, stale pointer targets and no-op history. The native menu probe constructs actual menu objects for all six locales in a temporary offline namespace, checks pending rows and translated warnings, and does not start audio or dispatch user menu events. That construction check is not a complete visual, hotplug or listening certification.

## Follow-up preference-action regressions

Tests reproduced an off Bass Assist decrement enabling its hidden remembered amount (35% became an enabled 25%), and an off Dynamic EQ control likewise using the cached strength. OFF now remains OFF on decrement; the first positive step is 10%. An unsupported output rejects Bass Assist activation. No-op controls cannot switch A/B, enable processing, materialize a device profile, rename the global EQ curve or change the TUI undo domain. Invalid rows and nonfinite/nonunit adjustment directions fail before writes.

A/B on a second endpoint previously prevented undoing the first endpoint's last tonal edit. Scoped undo now ignores comparison-only differences when checking history and restores only the target endpoint, preserving the other endpoint's current state. Unrelated tonal edits still invalidate it. CLI writes without an explicit device require a fresh, identified current output; an empty `sound set` and a default-targeted SaveDevice do not mutate settings.

The new `tests/preference_safety.rs` initially reproduced ten failing cases with one compatibility case passing; two additional state tests in `tests/unit/tui_actions.rs` reproduced global-control no-op and invalid-direction failures before those fixes. These are control/state regressions using isolated temporary files, not hardware, acoustic or subjective-listening evidence. DSP coefficients, callbacks, OS volume and default output are unchanged by this follow-up.

## Installation and recorded release checks

The installer tests use temporary application directories and actual built Maris binaries without starting system capture. They check dry-run/no-confirmation behavior, unverified-release rejection, identity and symlink rejection, preservation of unrelated files, upgrade backup, controlled promotion-failure rollback and refusal to replace a real open read-only MCP fixture process. That subprocess is owned by the test and never starts audio. These are installer/control tests, not driver, device or listening acceptance.

`verify_rounds.py --rounds 200` records 200 seeded offline rounds. Each runs a real generated-signal DSP/configuration case plus one of ten rotating regression suites. It uses multiple sample rates, original EQ curves and listening scenes, records logs and source hashes, rejects zero-test/ignored/failed results, and stops on failure or source drift. It is neither 200 independent audits nor 200 repetitions of the whole project suite. The full project checks and subjective/hardware gates stay separate. Local package metadata and release preflight explicitly retain these limitations.

## Input delivery and ablation evidence

A reproduced menu regression rejected comparison immediately after an approved scene because its displayed guard retained the pre-apply listening revision. The controller now acknowledges only the revision returned by its own transaction, preserving rejection of external edits. Native menu events use a main-loop wakeup, and macOS/Windows preset/output selection opens the explicit review dialog immediately; neither change alters the DSP path. The actual native item-ID dispatcher is exercised in isolated menu review, with the modal response injected rather than described as a human click.

TUI input coalesces only cursor-motion noise; meaningful press/release, drag, resize and keyboard events remain ordered. A real owned pseudo-terminal test sends 2,560 motion events plus sixteen plus/minus clicks and one paired Apply through the actual console, with an isolated state directory and held session lease to prevent capture. Draft state must commit once with the exact expected gain. This validates input delivery, not headphone playback.

The release ablation probe runs three generated signal conditions at four sample rates through the real Processor, comparing a deliberate all-effects reference against eight single-feature removals. It reports RMS, peak, crest, level-normalized output difference and processing wall time. Every variant retains gain safety and limiting. A nonzero contribution does not establish preferred sound; zero stereo-width contribution on mono is expected. No model, default, correction or audio callback was changed based on these synthetic results. The report is `.maris-review/feature-ablation.json`; the feature review in PRODUCT_GATES.md records what is retained, consolidated or still unavailable.

The standalone installers normally acquire only precompiled native packages from a version-pinned approved GitHub release. A transport regression reproduced a partial transfer failing to recover safely; Unix retries now start with a truncated private file, not an appended stdout stream. Kit collection regressions reproduced acceptance of opaque archive bytes, mismatched enclosed executables/source identities and mixed CI runs despite plausible outer hashes. A macOS-only test writes a test attribute to an isolated fixture payload, invokes the real native archiver and verifies that the payload attribute survives extraction. This is metadata/installation evidence, not notarization or publisher approval. Stable preparation still reruns the native release gate against the final extracted payload.

## Linux pulse-server processing

`audio/pulse` provides local-server discovery, application stream selection, owned temporary sinks, PCM processing, output following/pinning and per-route recovery. Independent Linux mixer application strips use separate private routes. Its PCM workers reuse the same deterministic rendering rules while keeping pipe reads and writes off native callbacks. Monitor preroll cannot advance the startup transition until the route controller arms the worker. Callback timing and worker timing remain separate metrics.

`tests/unit/pulse_stream.rs` checks the actual processor output across fragmented reads/writes, startup arming, nonfinite input, stop and revision delivery. `tests/unit/pulse_route.rs` drives the production parser and route controller through isolated subprocess fixtures, covering write-ahead recovery, self-exclusion, manual route changes, reused IDs, missing outputs and flat-volume rejection. These tests do not run a Linux audio server.

`tests/support/pulse_smoke.py` is the separate Linux native-server test. It creates its own Unix socket, PulseAudio process, silent output nodes and generated PCM clients; it runs Maris, checks parameter/output/application updates, kills only its own Maris child and checks the real recovery helper. CI calls it on Linux. Windows uses the WASAPI process-loopback backend with reversible session mute restoration. A declared CI job is not evidence that either native path passed on that platform, and silent nodes do not establish headphone behavior or listening quality. Direct PipeWire-only clients, long-duration device drift and real-device acceptance remain separate checks.

## Power-transition noise investigation

A user reported harsh electrical-like noise when disconnecting or reconnecting power. No physical power-cycle reproduction or electrical measurement is claimed. Fault injection did reproduce software defects that can create discontinuities: a running renderer accepted unready PCM, a missing source caused an abrupt sample step, and capture overflow left old queued PCM marked as continuous live audio. A separate regression showed an unstarted replacement renderer publishing its settings before any callback.

The shared renderer now separates invalid/missing PCM from digital silence, uses a 25 ms bounded discontinuity tail and recovery transition, and preserves normal steady-state samples and limiter attenuation. The live clock bridge resets stale history/backlog on observed overflow, timestamp gaps and native-callback interruptions. Native output interruption detection is tied to the actual callback block duration rather than a fixed 50 ms floor: a missed short hardware deadline restarts from silence before queued PCM can resume at full amplitude, while bounded scheduling jitter inside the callback budget is left untouched. macOS configuration notifications now include tap/aggregate/output properties plus CoreAudio device-list and follow-default-output changes. A USB/audio-device graph event immediately quarantines capture and clears queued PCM; an actual default-output change remains quarantined until the replacement pipeline is ready. Linux Pulse graph events similarly bypass the normal periodic health throttle. Independent mixer strips retain their own recovery, and master-output interruption clears stale input and delay state.

Tests use generated samples and owned callback buffers: four sample rates, short/long gaps, polarity changes, digital silence, malformed source data, callback-size-aware interruption, overflow, timestamp reset, and notification/acknowledgement races. The original routing, DSP, resampling, settings and undo tests remain required. `continuity` status counters are scoped to the current pipeline and explicitly do not claim to measure power state. Hardware power transitions, charger/dock/USB/Bluetooth behavior and actual listening acceptance remain open; these protections must not be presented as proof that the reported physical noise is cured.

## Verification

The regression suite covers DSP safety, shared headroom, bypass/A-B behavior, windowed-sinc quality, dynamic EQ, Bass Assist, correction-preserving output-switch transitions, bundled AutoEq matching/provenance, stable-device identity, listening undo, Music Context fallback/rate limiting and real MusicNN inference, output/application-scope controls, native routing state, multi-input/two-output mixing, bus alignment delay, explicit speech denoise, the Studio/pickers/settings input paths, menu dispatch, analysis freshness, MCP permissions and model-registry truthfulness.

The default test suite no longer needs a network AutoEq smoke test: its model index and release profile source are pinned build resources. Real-device listening, headphone/Bluetooth hotplug breadth, end-to-end latency, long-running clock behavior and native Windows/Linux/macOS execution remain separate validation requirements. A passing numerical test suite must not be described as a subjective listening certification.
